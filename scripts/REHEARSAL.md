# Repeatable local release acceptance

Run the paid product through a production Next server, a fresh PostgreSQL database, and fresh mock contracts on an owned Hardhat node. The runner is `rehearsal-local.mjs`; its helpers are CLI-only and are never imported by the application.

## Prerequisites and command

- Node 24 or newer.
- Root and `contracts/` dependencies installed (`npm ci` in each directory).
- A PostgreSQL 16 loopback server. The supplied local user needs `CREATEDB`; existing databases are not migrated, cleared, or reused.
- Enough space for a sanitized sibling source/build directory. Installed dependency files are hard-linked, so the source and temporary directory must reside on the same filesystem.

From the repository root, using a **local disposable server** and its own credentials:

```sh
node scripts/rehearsal-local.mjs --postgres-url 'postgres://USER@127.0.0.1:PORT/postgres?sslmode=disable' --out .scratch/rehearsal-result.json
```

The CLI requires a numeric loopback address. It rejects a public host, `localhost`, connection query overrides, and any query option except `sslmode=disable`. Do not pass a production connection string. The named database in the URL is only the administrative connection; the runner creates a new random `curb_rehearsal_<24 hex>` database and touches only that new database's application tables.

No environment file is copied or loaded. Child processes receive an OS-variable allowlist, plus only the local configuration generated by this invocation. API keys are generated per run, held in memory, and excluded from reports and logs. The chain uses unlocked local accounts; no private signing key is provided. Hardhat's startup output is discarded because it prints its well-known local test private keys.

## What is exercised

1. Fresh production-contract and mock compilation, deployment, actual mock top-ups, rate/bytecode verification, and chain indexing. The token-record/dry-run/deploy/duplicate-refusal CLI path uses a new randomly generated signer funded only by the owned local node.
2. A mock token donation creates a real reconciliation change. The paid HTTP journal must return that change, charge five cents, and agree with an independent PostgreSQL read.
3. Missing-key and malformed requests do not charge; an unfunded key receives `402`; two simultaneous funded HTTP calls charge exactly ten cents; re-indexing does not duplicate credit.
4. Subscriptions are created/cancelled through the actual HTTP API. Production `fanOut` and `deliver` functions post real HTTP bodies to a local receiver. One receiver returns `503`, then `204` on retry: only successful delivery is charged, a delivered condition is not resent, and cancellation prevents later delivery.
5. Production URL/DNS checks and the actual API still reject loopback webhook registrations. A CLI-only injected resolver and exact allowlisted transport map two `.invalid` test URLs to the receiver. No application SSRF rule or environment bypass is added.
6. The complete native application suite runs in the snapshot with PostgreSQL, credit top-up, position, incident-drill and credit-deployment fixtures populated. Any failed or skipped test fails this rehearsal. Tests that write incident evidence write only inside the snapshot.

The webhook test exercises the wire payload, status handling, ledger, retry and cancellation. It does **not** certify public DNS/TLS, a real third-party receiver, or wallet-extension behavior. Build tools may fetch compiler assets and Google fonts. App/payment/webhook transactions in this run stay on loopback and use mocks.

## Results and cleanup

Exit `0` means all assertions and cleanup succeeded. A nonzero exit means a failed assertion, startup/build failure, interruption, or incomplete cleanup. Read the JSON `state`, individual checks, boundaries, exact cent totals, snapshot hash and cleanup fields.

Every invocation writes redacted build/fixture logs to its own `.scratch/rehearsal-*` directory. The source/build snapshot is a sibling `.curb-rehearsal-*` directory identified in the report. Those files remain for inspection; they contain no environment files or generated API key. The runner stops only its own child process objects and drops only the database it successfully created. It leaves the PostgreSQL server and every pre-existing database running and unchanged. If the machine kills the runner without allowing cleanup, the report may be absent; identify its exact owned database/processes before cleaning anything manually.

The safety unit checks are independently runnable:

```sh
node --test tests/rehearsal-safety.test.ts
```

This acceptance is local evidence, not a mainnet launch approval or an independent contract review.

For a deliberate cleanup failure drill, add `--failure-drill` and choose a separate output report. This intentionally exits nonzero immediately after creating the owned database. A successful cleanup drill has that expected error and both cleanup booleans `true`; it is not a passing product acceptance. The PostgreSQL server remains running.
